## 1. Automatic Security Enforcement

### 1.1 Account Ownership Verification

**Property name:** Account ownership check

**What it enforces precisely:** `Account<T>` verifies that `account.owner == T::OWNER` before granting zero-copy access to the account's data. For types annotated with `#[account(discriminator = N)]`, `T::OWNER` is set to `crate::ID` via the `Owner` trait implemented by the `#[account]` macro. The check runs in `AccountLoad::check` during `Accounts::try_accounts` (generated by `#[derive(Accounts)]`) before any instruction handler logic executes. The check also rejects accounts where the owner is the System Program and lamports are zero, preventing use of an uninitialized system-owned account as a program account.

**What it does NOT enforce:** It does not verify the account's address (pubkey). An account owned by the correct program but at a different address passes this check unless a `has_one`, `address`, or `#[seeds]` constraint is also present. It does not verify account contents beyond discriminator and ownership.

**Trigger:** `Account<T>` field type in a `#[derive(Accounts)]` struct, where `T` is annotated with `#[account]`.

**If `UncheckedAccount` is used instead:** `UncheckedAccount` performs zero checks — no owner, no discriminator, no signer, no data validation. Unlike Anchor, Quasar does NOT require a `/// CHECK:` doc comment on `UncheckedAccount` fields; the compiler does not enforce documentation of unchecked account slots. This is a significant footgun compared to Anchor: the developer receives no tooling warning when leaving an account unchecked.

---

### 1.2 Account Discriminator Verification

**Property name:** Discriminator check on deserialization

**What it enforces precisely:** The `#[account(discriminator = N)]` attribute — where `N` is any non-zero constant expression — instructs the derive macro to prepend `N`'s byte representation to the account's on-chain data and to verify it during `AccountLoad::check`. The discriminator is encoded as the first bytes of account data. `try_deserialize` returns `AccountDiscriminatorMismatch` if the stored bytes do not match. From `lang/src/accounts/account.rs`, the check reads `data.starts_with(T::DISCRIMINATOR)` after verifying the owner.

**What it does NOT enforce:** Zero-value discriminators (`#[account(discriminator = 0)]`) are explicitly forbidden by the compiler (`zero_discriminator_account` compile-fail test). Quasar's compiler rejects all-zero discriminators because zeroed data is indistinguishable from a newly allocated account, preventing the developer from accidentally creating an unsafe state.

**Trigger:** `#[account(discriminator = N)]` on any `struct` or enum used as `T` in `Account<T>`.

**If `UncheckedAccount` is used instead:** No discriminator check. A `ZeroPod` or uninitialized account at the same address passes silently.

---

### 1.3 Signer Verification

**Property name:** Transaction signer check

**What it enforces precisely:** `Signer` (the Quasar account type defined in `lang/src/accounts/signer.rs`) sets `IS_SIGNER: bool = true` in its `AccountLoad` implementation. During `Accounts::try_accounts`, the generated code verifies `account.is_signer()` before the field is populated. The check fails with `ProgramError::MissingRequiredSignature`.

**What it does NOT enforce:** `Signer` does not verify that the signer is the authority for the specific operation. Business-logic authority binding requires a `has_one(field)` constraint on a companion `Account<T>` field, where `T` stores the expected authority address. `Signer` also does not check owner or data.

**Trigger:** `Signer` field type in `#[derive(Accounts)]`.

---

### 1.4 Program Identity Verification

**Property name:** Program account check

**What it enforces precisely:** `Program<T>` (defined in `lang/src/accounts/program.rs`) verifies `account.address() == T::ID` AND `account.executable == true` during `AccountLoad::check`. This prevents substituting a non-program account in a CPI target position and ensures the program is the expected one. The check returns `ProgramError::IncorrectProgramId` on mismatch.

**What it does NOT enforce:** It does not verify that the program has not been upgraded to a malicious version (upgradeable programs remain upgradeable independently of this check). It verifies the address at instruction parse time; it does not re-verify after any account state change.

**Trigger:** `Program<T>` field type where `T` implements the `Id` trait (providing `T::ID`).

---

### 1.5 Sysvar Address Verification

**Property name:** Sysvar canonical address check

**What it enforces precisely:** `Sysvar<T>` (defined in `lang/src/accounts/sysvar.rs`) verifies `view.address() == T::ID` during `AccountLoad::check`, returning `ProgramError::IncorrectProgramId` if the sysvar address does not match the canonical address for `T` (e.g., `Clock::ID`, `Rent::ID`). The `Sysvar::get()` method then casts the verified account data to `T` using an unchecked pointer cast whose safety is guaranteed by the prior address verification.

**What it does NOT enforce:** It does not verify sysvar data freshness or validity beyond the address check. Sysvar data is provided by the runtime and is considered authoritative once the address is verified.

**Trigger:** `Sysvar<T>` field type in `#[derive(Accounts)]`.

---

### 1.6 PDA Derivation Verification (Typed Seeds)

**Property name:** PDA seeds and bump verification via `#[seeds]` macro

**What it enforces precisely:** When an account type is annotated with `#[seeds(seed_bytes, param: Type, ...)]`, the `#[derive(Accounts)]` macro generates an `address = T::seeds(...)` constraint for `Account<T>` fields. This calls `quasar_lang::pda::verify_program_address(seeds, program_id, expected)` which computes SHA-256 of `seeds || program_id || "ProgramDerivedAddress"` directly via `sol_sha256` syscall (costing ~544 CU vs ~1,500 CU for `sol_create_program_address`). The canonical bump is returned via `ctx.bumps.<field_name>` and must be stored by the handler.

**What it does NOT enforce:** Quasar's `verify_program_address` does not call `find_program_address` — it verifies a provided address against the provided seeds (which must include the bump byte). If the developer passes user-supplied seeds or a non-canonical bump as a seed component, the PDA check may succeed for non-canonical derivations. The seeds must already include the bump byte.

**Trigger:** `#[seeds(...)]` attribute on an account type used with `address = T::seeds(...)` in an `#[derive(Accounts)]` struct.

---

### 1.7 `has_one` Constraint — Field Equality Check

**Property name:** Cross-account field equality

**What it enforces precisely:** `has_one(field_name)` in `#[account(has_one(field_name))]` verifies that `account.field_name == ctx.accounts.field_name.address()`, using Quasar's constant-time `keys_eq` comparison. Returns `QuasarError::HasOneMismatch` (error code 3002) on failure. The has_one check runs before PDA verification in Quasar (confirmed by test: "has_one rejects before PDA verification"). Zero-valued stored addresses (all-zero `Address`) are also caught and return a distinct error (`HasOneZeroed`, error code 3005).

**What it does NOT enforce:** It does not verify the type, ownership, or contents of the `field_name` account. It only checks key equality. An account that satisfies the key equality constraint but has incorrect ownership or discriminator requires additional `Account<T>` wrapping for full safety.

**Trigger:** `#[account(has_one(field_name))]` attribute on `Account<T>`.

---

### 1.8 Address Constraint — Exact Address Check

**Property name:** Exact pubkey equality

**What it enforces precisely:** `address = <expr>` verifies that the account's address equals the expression using `keys_eq`. Returns `QuasarError::AddressMismatch` (error code 3012). Used for hardcoded addresses (e.g., `address = [42u8; 32]`) and for PDA derivation via `address = T::seeds(...)`.

**Trigger:** `#[account(address = expr)]` attribute.

---

### 1.9 `mut` Constraint — Writability Enforcement

**Property name:** Writable account gating

**What it enforces precisely:** `#[account(mut)]` marks the field as requiring writable status. The generated code serializes the account back to chain after the handler exits. The framework also enforces that no mutability constraint is on a `Signer` that is not also `mut` when required by a behavior (e.g., `token_close` enforces `#[account(mut)]` at compile time via `requires_mut_behavior` check).

**What it does NOT enforce:** Quasar does not automatically assert that read-only accounts are NOT writable. A client can pass a writable account in a read-only position without the framework objecting.

**Trigger:** `#[account(mut)]`.

---

### 1.10 `init` Constraint — Reinitialization Prevention

**Property name:** Single-use initialization guard

**What it enforces precisely:** `#[account(mut, init, address = ...)]` marks the account for initialization. The generated code calls `quasar_lang::ops::init::init_account` which invokes the System Program's `create_account` CPI. The System Program rejects account creation if the target already has non-zero lamports, providing the reinitialization barrier. The framework then writes the discriminator to the account data.

**What it does NOT enforce:** Quasar's `init_if_needed` (available for SPL Token accounts in `quasar-spl`) does not provide this barrier — it passes through silently when the account already exists. When using `init_if_needed` for token/mint accounts, the handler must verify that the already-existing account has the correct mint, authority, and owner, which Quasar does enforce through token behavior validation.

**Trigger:** `#[account(mut, init, address = ...)]` on `Account<T>` fields.

---

### 1.11 `close` Constraint — Safe Account Closure

**Property name:** Atomic account closure

**What it enforces precisely:** `close(dest = field_name)` in `#[account(..., close(dest = field_name))]` schedules the account for closure on `AccountsExit::exit`. The `ops/close.rs` implementation: (1) transfers all lamports to `dest`; (2) zeroes all account data; (3) writes the `CLOSED_DISCRIMINATOR` bytes at offset 0; (4) reassigns the account owner to the System Program. This is a Quasar-specific close discriminator (sourced from the framework's close op, distinct from Anchor's `CLOSED_ACCOUNT_DISCRIMINATOR`). The discriminator overwrite prevents revival attacks because any subsequent `Account<T>` parsing will fail the discriminator check.

**What it does NOT enforce:** The framework does not constrain who the `dest` field is. The developer is responsible for ensuring `dest` is a trusted recipient. If `dest` is controlled by an attacker, the lamports flow to the attacker.

**Trigger:** `#[account(mut, close(dest = field_name))]` on `Account<T>`, with `dest` naming another account field.

---

### 1.12 Duplicate Mutable Account Detection (Header-Level)

**Property name:** Duplicate writability and signer detection

**What it enforces precisely:** Quasar's generated account parsing includes header-level duplicate detection. From the test suite (`header_nodup_mut`, `header_nodup_mut_signer`, `header_nodup_signer`): passing the same account key twice where both positions require `mut` is rejected at parse time with a header duplicate error. This prevents the classic "aliased mutable borrow" vulnerability where writing to two accounts that are actually the same key produces inconsistent state. Read-only duplicates are explicitly allowed (`header_dup_readonly`, `header_dup_signer` tests show these pass).

**What it does NOT enforce:** Two accounts at the same key where only one is `mut` and the other is read-only will pass the header check. The developer must add an explicit `require_keys_neq!` if same-key reads and writes would produce incorrect behavior.

**Trigger:** Automatic, generated by `#[derive(Accounts)]` for all `mut` account pairs.

---

### 1.13 `ZeroPod` / `Uninit` Account Type

**Property name:** Uninitialised account enforcement

**What it enforces precisely:** `Uninit<T>` (defined in `lang/src/accounts/uninit.rs`) is a special account type that enforces the account has NOT been initialized. It validates that the account data is entirely zeroed (via `checks::ZeroPod`). This prevents using `Uninit<T>` on already-initialised accounts, providing a different approach to reinitialization protection than `init`.

**What it does NOT enforce:** `Uninit<T>` does not create the account — the developer must call `init_account` or a System Program CPI to allocate space. It only asserts the current data is zero-valued.

**Trigger:** `Uninit<T>` field type in `#[derive(Accounts)]`.

---

### 1.14 Overflow Checks in Release Builds

**Property name:** Integer overflow detection

**What it enforces precisely:** Quasar's recommended `Cargo.toml` template sets `[profile.release] overflow-checks = true`. The Makefile's `check-runtime-panics` target rejects any `panic!`, `unreachable!`, `todo!`, or `unimplemented!` macro in `lang/src`, `spl/src`, and `derive/src` (with narrow exemptions for `lang/src/lib.rs`'s `"program aborted"` panic). This ensures no developer-written panics exist in framework code.

**What it does NOT enforce:** The overflow check setting is a Cargo profile option. Programs built without the recommended `Cargo.toml` configuration may not have this setting. The framework does not enforce its presence at runtime.

**Trigger:** `[profile.release] overflow-checks = true` in workspace `Cargo.toml`.

## 2. Developer Responsibilities

### 2.1 Authority Binding (Business Logic)

**Property name:** Stored authority matches signer

**Why the framework does not handle it:** Quasar's `Signer` type verifies the transaction signature but does not know which field of an `Account<T>` is the authority. The developer must add `has_one(authority)` to bind the signer to the stored field.

**Correct pattern:**
```rust
#[derive(Accounts)]
pub struct Withdraw {
    #[account(mut)]
    pub authority: Signer,
    #[account(
        mut,
        has_one(authority),             // verifies account.authority == authority.address()
        address = VaultAccount::seeds(authority.address()),
    )]
    pub vault: Account<VaultAccount>,
}
```

**Incorrect pattern developers commonly write:**
```rust
#[derive(Accounts)]
pub struct Withdraw {
    pub authority: Signer,         // transaction signer check only
    #[account(mut)]
    pub vault: Account<VaultAccount>,  // no has_one — any signer can drain any vault!
}
```

---

### 2.2 Storing the Canonical Bump

**Property name:** Canonical PDA bump persistence

**Why the framework does not handle it:** Quasar's `#[seeds]` derive provides `ctx.bumps.<field_name>` which is the canonical bump found by `based_try_find_program_address`. The framework does not automatically write this bump to account data; the developer must call `account.set_inner(Inner { bump: ctx.bumps.field, ... })`.

**Correct pattern:**
```rust
impl InitLiteralSeed {
    pub fn handler(&mut self, bumps: &InitLiteralSeedBumps) -> Result<(), ProgramError> {
        self.config.set_inner(ConfigAccountInner { bump: bumps.config }); // store canonical bump
        Ok(())
    }
}
```

**Incorrect pattern:**
```rust
impl InitLiteralSeed {
    pub fn handler(&mut self, _bumps: &InitLiteralSeedBumps) -> Result<(), ProgramError> {
        self.config.set_inner(ConfigAccountInner { bump: 0 }); // stores wrong bump — future validation fails or uses non-canonical value
        Ok(())
    }
}
```

---

### 2.3 `dest` Constraint Authorization on `close`

**Property name:** Closed account lamport destination authorization

**Why the framework does not handle it:** `close(dest = field_name)` transfers lamports to `dest` unconditionally. The framework does not verify that `dest` is a trusted account (e.g., the account owner, not an attacker-supplied address).

**Correct pattern:**
```rust
#[derive(Accounts)]
pub struct ClosePda {
    #[account(mut)]
    pub authority: Signer,
    #[account(
        mut,
        has_one(authority),          // binds authority to stored field
        address = UserAccount::seeds(authority.address()),
        close(dest = authority)      // lamports go to the validated authority
    )]
    pub user: Account<UserAccount>,
}
```

**Incorrect pattern:**
```rust
#[derive(Accounts)]
pub struct ClosePda {
    pub authority: Signer,
    pub recipient: UncheckedAccount,  // attacker-controlled destination
    #[account(mut, close(dest = recipient))]  // lamports drained to attacker
    pub user: Account<UserAccount>,
}
```

---

### 2.4 `UncheckedAccount` Manual Validation

**Property name:** Complete manual validation of unchecked accounts

**Why the framework does not handle it:** `UncheckedAccount` performs zero checks. Unlike Anchor, Quasar does not require a `/// CHECK:` comment — the compiler does not flag unchecked accounts at all. This is the highest-risk pattern in Quasar programs.

**Correct pattern:**
```rust
pub fn handler(ctx: Ctx<MyAccounts>) -> Result<(), ProgramError> {
    let acc = &ctx.accounts.unchecked;
    // All checks manual:
    require_keys_eq!(*acc.address(), EXPECTED_ADDRESS, ProgramError::InvalidArgument);
    require!(acc.owner() == &crate::ID, ProgramError::IllegalOwner);
    // ... etc.
    Ok(())
}
```

**Incorrect pattern:**
```rust
// UncheckedAccount with no subsequent validation — all properties unchecked
pub fn handler(ctx: Ctx<MyAccounts>) -> Result<(), ProgramError> {
    let data = ctx.accounts.unchecked.borrow_data(); // attacker-controlled data
    Ok(())
}
```

---

### 2.5 Instruction Argument Value Validation

**Property name:** Instruction data semantic validation

**Why the framework does not handle it:** Quasar validates instruction argument types (deserialization bounds, `OptionZc` tag values, fixed-capacity string/vec lengths via `#[max(N)]`). It does not validate semantic constraints (e.g., `amount > 0`, `threshold <= owners.len()`).

**Correct pattern:**
```rust
pub fn create(ctx: Ctx<Create>, threshold: u8) -> Result<(), ProgramError> {
    let owner_count = ctx.remaining_accounts.len() as u8;
    require!(threshold > 0, ProgramError::InvalidArgument);
    require!(threshold <= owner_count, ProgramError::InvalidArgument);
    Ok(())
}
```

**Incorrect pattern:**
```rust
pub fn create(ctx: Ctx<Create>, threshold: u8) -> Result<(), ProgramError> {
    // No validation — threshold could be 0 or exceed owner count
    state.threshold = threshold;
    Ok(())
}
```

---

### 2.6 Post-CPI State Re-reading

**Property name:** Account state consistency after CPI

**Why the framework does not handle it:** Quasar's zero-copy account model reads account data through raw pointers (`data_ptr()`). After a CPI that modifies account state, the in-memory pointers may reflect stale data. The framework does not automatically invalidate or reload cached state.

**Correct pattern:**
```rust
pub fn complex_op(ctx: Ctx<ComplexOp>) -> Result<(), ProgramError> {
    let before = ctx.accounts.vault.amount;
    ctx.accounts.token_program.transfer(/* ... */)?;
    // Re-read after CPI: zero-copy view reflects updated on-chain data
    // because AccountView pointers track the runtime's account data region.
    let after = ctx.accounts.vault.amount; // safe: Quasar AccountView is a view into live data
    require!(after == before - amount, ProgramError::Custom(0));
    Ok(())
}
```

**Note:** Quasar's `cpi_mut_readback` tests verify that data written via `set_inner` before a CPI survives the CPI round-trip. The concern is primarily with data read by dereferencing `Account<T>` before and after a CPI that modifies it — the second read through the same pointer reflects the updated data correctly because the AccountView pointers track the runtime's memory region.

### 2.7 `#[instruction(raw)]` — Complete Manual Responsibility

**Property name:** Raw instruction safety

**Why the framework does not handle it:** `#[instruction(discriminator = N, raw)]` emits the function body unchanged — no account parsing, no constraint evaluation, no discriminator check. The handler receives only a `Context` containing a raw `&[AccountView]` slice and `&[u8]` data. All validation is manual.

**Correct pattern:**
```rust
#[instruction(discriminator = 1, raw)]
pub fn update_oracle(ctx: Context) -> Result<(), ProgramError> {
    if ctx.accounts.is_empty() {
        return Err(ProgramError::NotEnoughAccountKeys);
    }
    let oracle = &ctx.accounts[0];
    if oracle.owner() != &crate::ID {
        return Err(ProgramError::IllegalOwner);
    }
    // ... full manual validation
    Ok(())
}
```

**Incorrect pattern:**
```rust
#[instruction(discriminator = 1, raw)]
pub fn update_oracle(ctx: Context) -> Result<(), ProgramError> {
    // No validation on any account — equivalent to no-framework native Rust
    let data = ctx.accounts[0].borrow_data();
    Ok(())
}
```

### 2.8 Remaining Accounts — No Automatic Type Checking

**Property name:** Remaining accounts validation

**Why the framework does not handle it:** Quasar supports typed `remaining_accounts` parsing via `RemainingItem<'input>` trait implementations for `Signer`, `SystemAccount`, `UncheckedAccount`, and `Account<T>`. However, the developer must declare the type of remaining accounts and ensure the IDL description matches. Accounts passed in remaining positions that exceed the declared maximum (`RemainingAccountsOverflow`, error 3002 class) are rejected, but the individual account properties (owner, discriminator) are checked only if the remaining item type is `Account<T>` or `Signer` — not for `UncheckedAccount`.

**Correct pattern:**
```rust
// Declare typed remaining accounts — Quasar validates signer + owner automatically
#[remaining_accounts(signers: Signer, max = 8)]
pub struct MultisigApprove { /* ... */ }
```

**Incorrect pattern:**
```rust
// UncheckedAccount remaining accounts — no property validation
#[remaining_accounts(accounts: UncheckedAccount, max = 8)]
pub struct DangerousInstruction { /* ... */ }
// handler must manually validate each remaining account
```

## 3. Framework-Specific Vulnerability Patterns

### 3.1 `UncheckedAccount` Without Documentation or Validation

**Pattern name:** Silent unchecked accounts (`missing_ownership_check`, `missing_signer_check`)

**What the developer writes:** A field typed as `UncheckedAccount` in `#[derive(Accounts)]`, used without any validation in the handler.

**Why this framework makes it more likely:** Unlike Anchor, Quasar does NOT require a `/// CHECK:` comment on `UncheckedAccount` fields. The compiler emits no warning or error. This means a developer can silently introduce a completely unchecked account slot with no tooling feedback.

**Formal property that should hold but does not:**
`guard: account.owner == expected_owner AND account.data[..discriminator.len()] == discriminator`

**Vulnerable code:**
```rust
use quasar_lang::prelude::*;
solana_address::declare_id!("11111111111111111111111111111112");

#[account(discriminator = 1)]
pub struct Config { pub authority: Address }

#[derive(Accounts)]
pub struct Execute {
    pub signer: Signer,
    pub config: UncheckedAccount, // No warning — no check — attacker supplies any account
}

#[program]
mod vuln {
    use super::*;
    #[instruction(discriminator = 0)]
    pub fn execute(ctx: Ctx<Execute>) -> Result<(), ProgramError> {
        // Treats UncheckedAccount as a Config — no runtime check
        let data = ctx.accounts.config.borrow_data();
        let authority = Address::try_from(&data[1..33]).unwrap();
        require_keys_eq!(*ctx.accounts.signer.address(), authority, ProgramError::InvalidAccountData);
        Ok(())
    }
}
```

**Correct code:**
```rust
#[derive(Accounts)]
pub struct Execute {
    pub signer: Signer,
    #[account(has_one(authority))]
    pub config: Account<Config>,  // auto: owner + discriminator + has_one
}
```

**kani::assert! expression:**
```rust
kani::assert!(
    ctx.accounts.config.owner() == &crate::ID,
    "config must be owned by this program"
);
kani::assert!(
    ctx.accounts.config.borrow_data().starts_with(Config::DISCRIMINATOR),
    "config discriminator must match"
);
```

**QEDSpec clause:**
```
guard: config.owner == program_id
guard: config.data[..discriminator.len()] == Config::DISCRIMINATOR
guard: config.authority == signer.key()
```

### 3.2 Missing Bump Storage Leading to PDA Validation Failure

**Pattern name:** Canonical bump not persisted (`init_without_pda`)

**What the developer writes:** An `init` instruction that does not store `ctx.bumps.<field_name>` in the account data, causing subsequent instructions that use `address = T::seeds(stored_bump)` to fail or use a wrong bump.

**Why this framework makes it more likely:** Quasar's `#[seeds]` derive automatically derives the canonical bump at init time (via `based_try_find_program_address` at ~544 CU). The framework surfaces the bump via `ctx.bumps.field_name` but does not automatically write it to account data. This split between derivation and storage is a Quasar-specific footgun not present in Anchor (which stores bumps in the `Bumps` struct but also relies on the developer to call `set_inner` with the correct value).

**Formal property that should hold but does not:**
`establishes: account.bump == ctx.bumps.account_field (canonical bump)`

**Vulnerable code:**
```rust
#[account(discriminator = 1, set_inner)]
#[seeds(b"config")]
pub struct ConfigAccount { pub bump: u8 }

impl InitLiteralSeed {
    pub fn handler(&mut self, bumps: &InitLiteralSeedBumps) -> Result<(), ProgramError> {
        self.config.set_inner(ConfigAccountInner { bump: 255 }); // hardcoded — wrong if canonical != 255
        Ok(())
    }
}
```

**Correct code:**
```rust
impl InitLiteralSeed {
    pub fn handler(&mut self, bumps: &InitLiteralSeedBumps) -> Result<(), ProgramError> {
        self.config.set_inner(ConfigAccountInner { bump: bumps.config }); // canonical bump from ctx
        Ok(())
    }
}
```

**kani::assert! expression:**
```rust
kani::assert!(
    ctx.accounts.config.bump == ctx.bumps.config,
    "stored bump must equal canonical bump from derivation"
);
```

**QEDSpec clause:**
```
establishes: config.bump == ctx.bumps.config
```

### 3.3 `has_one` Without `Signer` — Authority Binding Without Signature

**Pattern name:** Authority field match without signer check (`missing_signer_check`)

**What the developer writes:** A `has_one(authority)` constraint on an `Account<T>`, with `authority` typed as `UncheckedAccount` instead of `Signer`. The field equality check passes but the account never signed the transaction.

**Why this framework makes it more likely:** Quasar's `has_one` checks key equality between stored field and the companion account. If the companion account is `UncheckedAccount`, the attacker can pass any account they know the key of — including an account they do NOT control — and satisfy `has_one` without ever signing.

**Formal property that should hold but does not:**
`guard: authority.is_signer == true`

**Vulnerable code:**
```rust
#[derive(Accounts)]
pub struct Withdraw {
    pub authority: UncheckedAccount,  // NOT a Signer — anyone can pass authority's pubkey
    #[account(mut, has_one(authority))]  // key equality passes — no signature check
    pub vault: Account<VaultAccount>,
}
```

**Correct code:**
```rust
#[derive(Accounts)]
pub struct Withdraw {
    pub authority: Signer,            // transaction signature enforced
    #[account(mut, has_one(authority))]
    pub vault: Account<VaultAccount>,
}
```

**kani::assert! expression:**
```rust
kani::assert!(
    ctx.accounts.authority.is_signer(),
    "authority must be a transaction signer"
);
kani::assert!(
    ctx.accounts.vault.authority == *ctx.accounts.authority.address(),
    "stored authority must match signer"
);
```

**QEDSpec clause:**
```
guard: authority.is_signer == true
guard: vault.authority == authority.key()
```

### 3.4 PDA Sharing via Non-Unique Seeds

**Pattern name:** Over-broad seed sets creating shared authority (`permissionless_state_write`)

**What the developer writes:** A PDA derived from global seeds only (e.g., `#[seeds(b"config")]`) used as an authority over per-user state, allowing all users to share one PDA authority.

**Why this framework makes it more likely:** Quasar's `#[seeds]` macro makes PDA derivation ergonomic. Developers may use minimal seeds (e.g., global constants) for simplicity, inadvertently creating a shared-authority vulnerability.

**Formal property that should hold but does not:**
`guard: forall users u1 != u2: pda(u1) != pda(u2)` when the PDA governs per-user assets.

**Vulnerable code:**
```rust
#[account(discriminator = 1, set_inner)]
#[seeds(b"pool")]  // Global — all users share one pool PDA
pub struct PoolAccount { pub owner: Address, pub balance: u64, pub bump: u8 }
// Any user who knows the seed can derive the same PDA and satisfy address checks
```

**Correct code:**
```rust
#[account(discriminator = 1, set_inner)]
#[seeds(b"pool", authority: Address)]  // Per-user — authority in seeds
pub struct PoolAccount { pub authority: Address, pub balance: u64, pub bump: u8 }
// Each user has a unique PoolAccount PDA
```

**kani::assert! expression:**
```rust
kani::assert!(
    ctx.accounts.pool.authority == *ctx.accounts.authority.address(),
    "pool owner must match signer authority"
);
```

**QEDSpec clause:**
```
guard: pool.authority == authority.key()
```

### 3.5 `init_if_needed` for Program Accounts — Reinitialization Risk

**Pattern name:** Reinitialization via `init_if_needed` without guard (`insecure_initialisation`)

**What the developer writes:** Using `init_if_needed` behavior for a program `Account<T>` without verifying the account's fields are correct after initialization.

**Why this framework makes it more likely:** Quasar's `init_if_needed` for SPL Token accounts validates mint and authority when the account already exists. For general program accounts, `init_if_needed` is less common in Quasar than Anchor, but developers who implement custom "init if needed" logic in their handlers may skip the reinit guard.

**Formal property that should hold but does not:**
`requires: account.is_uninitialized OR (account.authority == expected_authority AND account.data[0] == DISCRIMINATOR)`

**Vulnerable code:**
```rust
// Handler that "initializes" regardless of existing state
pub fn initialize(ctx: Ctx<Initialize>) -> Result<(), ProgramError> {
    ctx.accounts.state.set_inner(StateInner {
        authority: *ctx.accounts.payer.address(), // overwrites existing authority!
        value: 0,
        bump: ctx.bumps.state,
    });
    Ok(())
}
```

**Correct code:**
```rust
// Use `init` constraint — the System Program CPI rejects already-existing accounts
#[account(mut, init, address = StateAccount::seeds(payer.address()))]
pub state: Account<StateAccount>,
```

**kani::assert! expression:**
```rust
// Check performed before any set_inner call:
kani::assert!(
    ctx.accounts.state.borrow_data().iter().all(|&b| b == 0),
    "account must be uninitialized before writing"
);
```

**QEDSpec clause:**
```
requires: state.data is zeroed (account uninitialized)
establishes: state.authority == authority.key()
establishes: state.data[..discriminator.len()] == StateAccount::DISCRIMINATOR
```

### 3.6 Arbitrary CPI via `UncheckedAccount` Program Target

**Pattern name:** Unvalidated CPI target program (`arbitrary_cpi`)

**What the developer writes:** A CPI built using an account in the `UncheckedAccount` position as the program target, without verifying its address.

**Why this framework makes it more likely:** Quasar's `Program<T>` type verifies the program address. `UncheckedAccount` does not. Developers building raw CPIs or supporting multiple token programs sometimes reach for `UncheckedAccount` instead of `Interface<TokenInterface>`.

**Formal property that should hold but does not:**
`guard: token_program.address() == SPL_TOKEN_ID OR token_program.address() == TOKEN_2022_ID`

**Vulnerable code:**
```rust
#[derive(Accounts)]
pub struct Transfer {
    pub from: Account<Token>,
    pub to: Account<Token>,
    pub authority: Signer,
    pub token_program: UncheckedAccount,  // Not validated — attacker supplies malicious program
}
```

**Correct code:**
```rust
use quasar_spl::prelude::*;

#[derive(Accounts)]
pub struct Transfer {
    pub from: Account<Token>,
    pub to: Account<Token>,
    pub authority: Signer,
    pub token_program: Program<TokenProgram>,   // Enforces SPL_TOKEN_ID
    // OR: pub token_program: Interface<TokenInterface>; // Allows SPL Token OR Token-2022
}
```

**kani::assert! expression:**
```rust
kani::assert!(
    quasar_lang::keys_eq(ctx.accounts.token_program.address(), &quasar_spl::SPL_TOKEN_ID)
    || quasar_lang::keys_eq(ctx.accounts.token_program.address(), &quasar_spl::TOKEN_2022_ID),
    "token_program must be a known token program"
);
```

**QEDSpec clause:**
```
guard: token_program.key() == SPL_TOKEN_ID OR token_program.key() == TOKEN_2022_ID
```

### 3.7 Account Migration — Source/Target Discriminator Collision

**Pattern name:** Migration discriminator prefix collision (`paired_validator_mismatch`)

**What the developer writes:** A `Migration<From, To>` where `From::DISCRIMINATOR` is a prefix of `To::DISCRIMINATOR` (or vice versa), allowing a partially-migrated account to be accepted as either type.

**Why this framework makes it more likely:** Quasar provides a formal account migration system (`Migration<From, To>` in `lang/src/accounts/migration.rs`) with compile-time checks. The compile-time assertion `_DISC_NEQ` verifies that neither discriminator is a prefix of the other. However, this check is only enforced at compile time for the migration type; if discriminators are defined manually or changed after deployment, the assertion is not re-evaluated.

**What Quasar enforces:** At compile time: `From::DISCRIMINATOR` must not be a prefix of `To::DISCRIMINATOR`, and vice versa. At runtime: before migration, the account data must start with `From::DISCRIMINATOR` (not `To::DISCRIMINATOR`). After migration, the account data starts with `To::DISCRIMINATOR`. Both `From` and `To` must have the same `OWNER`.

**Formal property that should hold but does not:**
Ensured at compile time, but if discriminator constants are modified post-deployment:
`guard: From::DISCRIMINATOR is NOT a prefix of To::DISCRIMINATOR`

**Vulnerable code (compile-fail in Quasar — shown for educational purposes):**
```rust
// This would be caught at compile time by _DISC_NEQ assert:
#[account(discriminator = 1)]      // [1]
pub struct OldConfig { /* ... */ }

#[account(discriminator = 1, 2)]   // [1, 2] — prefix collision with OldConfig!
pub struct NewConfig { /* ... */ }
```

**Correct code:**
```rust
#[account(discriminator = 1)]      // [1]
pub struct OldConfig { /* ... */ }

#[account(discriminator = 2)]      // [2] — no prefix relation
pub struct NewConfig { /* ... */ }
```

**QEDSpec clause:**
```
guard: From::DISCRIMINATOR is not a prefix of To::DISCRIMINATOR
guard: account.data.starts_with(From::DISCRIMINATOR) (before migration)
ensures: account.data.starts_with(To::DISCRIMINATOR) (after migration)
```

## 4. Trust Boundaries

### Attacker-Controlled Inputs

Every account in the instruction is attacker-controlled until the generated `Accounts::try_accounts` code accepts or rejects it. The following inputs bypass automatic protections:

- **Any `UncheckedAccount` field:** No checks are performed. In Quasar, unlike Anchor, no documentation requirement (`/// CHECK:`) enforces acknowledgment of this risk.
- **Instruction argument values:** Quasar validates argument types (deserialization, `OptionZc` tag, `#[max(N)]` bounds) but not semantic invariants. `amount > 0`, `threshold <= owners.len()`, and similar business constraints must be written manually.
- **`remaining_accounts` when typed as `UncheckedAccount`:** The accounts count is bounded by `max` but individual account properties are unchecked.
- **CPI program accounts typed as `UncheckedAccount`:** The attacker controls the CPI target.
- **PDA seeds containing instruction arguments:** If a seed value comes from instruction data (e.g., `index: u64` in `#[seeds(b"indexed", authority: Address, index: u64)]`), the attacker controls the index — only the derivation address is verified, not whether the index is semantically valid.

### Framework Assumptions the Developer Must Verify

- **`has_one` companion must be a `Signer`:** `has_one(authority)` alone does not enforce the companion is a signer. The developer must ensure the `authority` field type is `Signer`, not `UncheckedAccount`.
- **`close(dest = field)` destination trust:** The developer must constrain `dest` to a trusted address (e.g., `dest = authority` where `authority: Signer` bound by `has_one`).
- **Bump persistence:** The canonical bump from `ctx.bumps.<field>` must be stored in the account data by the developer inside `set_inner`.
- **Semantic argument invariants:** Type validity of arguments is enforced by Quasar's `InstructionArg` deserialization; value invariants are not.
- **`#[instruction(raw)]` handlers:** All account validation is the developer's responsibility.

### CPI Trust Boundaries

**What Quasar verifies about CPI targets:** When `Program<T>` is used, Quasar verifies `address == T::ID` and `executable == true`. Quasar's typed CPI module functions (e.g., `token_program.transfer(...)` on `Program<TokenProgram>`) embed the target program address from the verified `Program<T>` wrapper. For `Interface<TokenInterface>`, Quasar's `is_token_program` verifies the address is one of `SPL_TOKEN_ID` or `TOKEN_2022_ID`.

**What the developer must verify:** That accounts passed within the CPI are correctly ordered and typed for the callee. Quasar's typed CPI builders handle this for SPL operations, but raw `CpiCall::new` / `CpiDynamic` calls require manual account ordering. After CPIs, re-read account state if subsequent logic depends on values that may have changed.

**`UncheckedAccount` CPI target:** No program address check is performed. Any executable account address is accepted.

### What `UncheckedAccount` Leaves Unprotected

`UncheckedAccount` leaves ALL of the following unprotected: owner (program), discriminator (type), signer status, PDA derivation, writability assertion (beyond runtime enforcement), and any field equality relationship to other accounts. Unlike Anchor, there is no compile-time documentation requirement. A Quasar program with `UncheckedAccount` fields that are not manually validated is equivalent in risk to a Pinocchio program with no TryFrom checks.

## 5. Discriminator and Type Safety

### How Account Types Are Distinguished

Every `struct` annotated with `#[account(discriminator = N)]` receives a discriminator computed from `N` — an arbitrary constant expression (integer literal, constant name, byte literal, or byte array). The discriminator is the first bytes of the serialized account data, written by `try_serialize` and verified by `try_deserialize`.

Quasar's `one_of` feature (`#[account(one_of, implements(Trait))]`) allows an enum of account types, where each variant has its own discriminator. The `Account<ConsensusAccount>` type accepts an account whose discriminator matches any variant and provides typed access via `account.variant()` returning a `ConsensusAccountRef`.

### What Prevents Type Confusion Attacks

`Account<T>` verifies both `owner == T::OWNER` AND `data.starts_with(T::DISCRIMINATOR)` before granting access. Two structs owned by the same program with the same field layout are distinguished by their discriminators. Zero discriminators are rejected at compile time (`zero_discriminator_account` compile-fail test rejects `discriminator = 0`, `discriminator = [0,0,0]`, and `discriminator = ZERO_CONSTANT`).

### Where the Discriminator Check Happens and Whether It Can Be Bypassed

The check occurs in `AccountLoad::check` called during `Accounts::try_accounts`, before any instruction handler code runs. It can be bypassed by:
- Using `UncheckedAccount` and manually reading data without a discriminator check.
- Using `from_account_view_unchecked` (marked `unsafe`, safety contract requires the caller to have already validated the discriminator).
- Using `#[instruction(raw)]` handler which skips all account parsing.
- Constructing a custom account type that implements `AccountLoad` with a no-op `check` method.

### Developer Responsibility Beyond Framework Enforcement

- Define unique, non-zero discriminator values for every account type.
- Store the `#[account]` annotated struct's discriminator value in the Quasar IDL and use consistent values across client and program.
- Ensure migration discriminators satisfy the non-prefix property.
- When adding new account types to an existing program, verify that new discriminators do not conflict with existing ones.
- `one_of` enum discriminators: each variant must have a distinct discriminator from all others.

## 6. Initialization and Lifecycle

### How Quasar Prevents Reinitialization Attacks

`#[account(mut, init, address = T::seeds(...))]` invokes the System Program's `create_account` CPI via `quasar_lang::ops::init::init_account`. The System Program rejects creation of accounts with non-zero lamports, providing the primary reinitialization guard. After creation, the framework writes the discriminator. Any subsequent `Account<T>` parse will succeed (discriminator matches) — the discriminator alone does not prevent reinit if the account is closed and re-opened. The `init` constraint prevents reinit by failing at the System Program CPI level.

### What the Developer Must Do During Initialization

- Store the canonical bump from `ctx.bumps.<field>` by calling `account.set_inner(Inner { bump: ctx.bumps.field, ... })`.
- Set all authority and relationship fields; Quasar does not infer which fields are authority fields.
- For accounts with `#[seeds]` derive: the address check at parse time verifies the correct PDA is in the `init` position, but the bump must still be manually stored.
- Verify that any `init_if_needed` usage includes companion checks for existing account correctness.

### How Quasar Handles Account Closure

`close(dest = field)` in the `#[account]` constraint schedules the account for the Quasar close sequence after the handler exits (in `AccountsExit::exit`): (1) lamport transfer to `dest`; (2) data zeroed; (3) Quasar's closed discriminator written at offset 0; (4) owner reassigned to System Program. This sequence prevents same-transaction revival because any subsequent discriminator check will find the closed-discriminator bytes rather than the account type's discriminator.

### What Lifecycle Transitions the Framework Tracks vs. Developer Responsibility

**Quasar tracks:** Account exists (created by `init`), account is closed (destroyed by `close`), account is being migrated (`Migration<From, To>` in progress).

**Developer must track:** Application state machine transitions (e.g., `Pending → Active → Settled`), multi-step authorization states, timelock expiry, whether a field like `did_execute` has been set. These must be stored as fields in the account data and checked with `require!` at the start of each instruction handler.

## 7. Arithmetic Safety

### Default Behavior

Quasar's recommended Cargo workspace sets `[profile.release] overflow-checks = true`. The Makefile enforces `check-runtime-panics` which rejects any `panic!`, `unreachable!`, `todo!`, or `unimplemented!` in framework code. With `overflow-checks = true`, all primitive integer arithmetic panics on overflow in both debug and release builds.

### What Is Safe by Default

With `overflow-checks = true`: all `+`, `-`, `*` on primitives panic on overflow. Quasar's PDA derivation (`verify_program_address`, `based_try_find_program_address`) uses `MaybeUninit` for pointer arithmetic with explicit bounds proofs via Kani (`verify_program_address_indices_within_bounds`). The framework's `write_bytes` for `UncheckedAccount` uses `checked_add` for offset arithmetic, returning `ProgramError::AccountDataTooSmall` on overflow.

### What Requires Explicit Checked Variants

- **`as` casts** (`u128 as u64`) silently truncate regardless of `overflow-checks`. Use `u64::try_from(value)?`.
- **Wrapping arithmetic** (`wrapping_add`, etc.) intentionally bypasses the flag.
- **Lamport arithmetic** should use `.checked_add()` / `.checked_sub()` for clarity even with the flag, to produce meaningful error messages rather than panics.
- **Division by zero** panics regardless; use `.checked_div()` when divisor may be zero.
- **`PodU64` and similar pod types** in Quasar's `pod.rs` are `repr(C)`, `#[derive(Pod, Zeroable)]`. Reading and writing them through the zero-copy pointer is not arithmetic — the values are stored and retrieved as little-endian bytes.

### Framework-Specific Arithmetic Utilities

Quasar does not provide arithmetic helper functions beyond enabling the Rust overflow flag. Use Rust's `.checked_add()`, `.checked_sub()`, `.checked_mul()`, `.checked_div()`. Quasar's Kani proof harnesses in `lang/kani/` and `metadata/kani/` verify instruction data layout arithmetic (prefix writes, offset correctness) — these proofs cover framework code, not developer handler code.

## 9. Common Audit Findings in This Framework

### 9.1 `missing_signer_check`

**Why common in Quasar:** Quasar's `has_one(authority)` constraint checks field equality but does not require the companion to be a `Signer`. A developer who sees `has_one` and concludes the operation is "authorized" but uses `UncheckedAccount` for the companion has bypassed the signature check entirely. Since Quasar provides no `/// CHECK:` enforcement on `UncheckedAccount`, this mistake produces no compile-time warning.

**Framework feature contributing:** The separation between `has_one` (key equality) and `Signer` (signature) is not enforced by the framework. Quasar does not emit a compile-time warning when `has_one` references an `UncheckedAccount` field.

**Gap analysis detection:** For every `has_one(authority)` constraint, verify that the referenced field is typed as `Signer`, not `UncheckedAccount`. Any `has_one` referencing an `UncheckedAccount` is a candidate for `missing_signer_check`.

---

### 9.2 `missing_ownership_check`

**Why common in Quasar:** `UncheckedAccount` performs no owner check, and Quasar — unlike Anchor — does not require a `/// CHECK:` comment forcing the developer to justify the choice. Programs that use `UncheckedAccount` for CPI passthrough accounts or dynamic accounts without adding manual ownership checks in the handler are silently vulnerable.

**Framework feature contributing:** No `/// CHECK:` requirement on `UncheckedAccount` fields. The compiler accepts unchecked accounts without any acknowledgment.

**Gap analysis detection:** Find all `UncheckedAccount` fields in `#[derive(Accounts)]` structs. For each, verify that the handler contains an explicit `account.owner() == &expected_program_id` check or a `require_keys_eq!` address check before accessing data. Flag any that lack both.

---

### 9.3 `init_without_pda` (Missing Bump Storage)

**Why common in Quasar:** Quasar's `#[seeds]` derive and `ctx.bumps` pattern creates the canonical bump but does not persist it automatically. The developer must call `set_inner` with `bump: ctx.bumps.field`. Programs that initialize accounts without storing the canonical bump will have incorrect bump values in their account data, causing subsequent `address = T::seeds(stored_bump)` validations to fail or to use non-canonical values.

**Framework feature contributing:** The split between bump derivation (automatic, via `based_try_find_program_address`) and bump storage (manual, via `set_inner`) is a Quasar-specific pattern not enforced by the framework.

**Gap analysis detection:** For every `init` account that has a `#[seeds]` derive on its type, verify that the handler's `set_inner` call includes `bump: ctx.bumps.<field_name>`. Any `set_inner` that hardcodes the bump (e.g., `bump: 255`) or omits it is a candidate for `init_without_pda`.

---

### 9.4 `lifecycle_violation` (Close Constraint Destination Not Authorized)

**Why common in Quasar:** The `close(dest = field)` constraint transfers lamports to `dest` atomically. If `dest` is an `UncheckedAccount` that the attacker controls, all lamports from the closed account flow to the attacker. This is especially dangerous because the `close` constraint is easy to use (one attribute) and the `dest` authorization is not enforced by the framework.

**Framework feature contributing:** The `close` constraint does not constrain who `dest` is. The developer must add separate authorization (e.g., `has_one(authority)` on a companion account, with `close(dest = authority)` to send lamports to the validated authority).

**Gap analysis detection:** For every `close(dest = field)` constraint, verify that `field` is typed as `Signer` or as an `Account<T>` constrained by `has_one` to a signer field. Any `close(dest = x)` where `x` is an `UncheckedAccount` not further validated is a lifecycle_violation candidate.

---

### 9.5 `arbitrary_cpi`

**Why common in Quasar:** Quasar's `Program<T>` enforces program ID. However, programs that support both SPL Token and Token-2022 may reach for `UncheckedAccount` as a shortcut instead of `Interface<TokenInterface>`. Additionally, programs that build raw `CpiCall` or `CpiDynamic` instructions from `UncheckedAccount` program fields bypass the typed safety entirely.

**Framework feature contributing:** `Interface<T>` is available in `quasar-spl` for the token interface, but developers who use `UncheckedAccount` for program accounts in the core `quasar-lang` layer get no key check. There is no framework enforcement that CPI target fields must use `Program<T>` or `Interface<T>`.

**Gap analysis detection:** Scan for `CpiCall::new(program.address(), ...)` and `CpiDynamic::new(program.address(), ...)` where `program` is an `UncheckedAccount` rather than `Program<T>`. Verify that a preceding `require_keys_eq!` or `address` constraint validates the program address. Any raw CPI using an unchecked program field without address validation is `arbitrary_cpi`.

```
Topic: has_one Constraint — Cross-Account Field Equality
Applies to: Any instruction where stored authority/mint/vault must match a companion account

has_one(authority) verifies account.authority == ctx.accounts.authority.address() using constant-time keys_eq. Returns QuasarError::HasOneMismatch (error 3002). Zero-valued stored addresses return HasOneZeroed (error 3005). IMPORTANT: has_one does NOT check signer status. has_one runs BEFORE PDA verification in Quasar (confirmed by test suite). The companion field must be Signer for authority-gating. has_one + UncheckedAccount = key equality only, no signature. has_one + Signer = key equality + signature. Both are required for authority operations. QEDSpec: guard: account.authority == authority.key() (from has_one); guard: authority.is_signer == true (from Signer type).
```

```
Framework: Quasar
Topic: Account Closure — close Constraint and Destination Authorization
Applies to: All instructions that close accounts

close(dest = field_name) in #[account(mut, close(dest = field_name))] schedules closure after the handler: (1) lamports transferred to dest; (2) data zeroed; (3) Quasar closed discriminator written; (4) owner reassigned to System Program. Prevents revival attacks. CRITICAL DEVELOPER RESPONSIBILITY: Quasar does NOT constrain who dest is. If dest is UncheckedAccount, lamports flow to an attacker. Pattern: always use close(dest = authority) where authority: Signer bound by has_one(authority) on the account. Destination must be a validated trusted recipient. QEDSpec: ensures: account.lamports == 0; ensures: account.data has closed discriminator; guard: dest.key() == trusted_authority.key().
```

```
Framework: Quasar
Topic: Reinitialization Prevention — init Constraint and init_if_needed
Applies to: All initialization instructions

#[account(mut, init, address = T::seeds(...))] invokes System Program create_account CPI via quasar_lang::ops::init::init_account. System Program rejects accounts with non-zero lamports, preventing reinit. After creation, the framework writes the discriminator. init_if_needed (quasar-spl token accounts) does NOT provide this barrier — it passes through on existing accounts but validates mint/authority/owner for token accounts. For general program accounts: use init, not manual initialization logic that might skip the reinit guard. Any instruction that writes account.set_inner() without an init constraint or uninitialized check is insecure_initialisation. QEDSpec: requires: account.lamports == 0 (for init path).
```

```
Quasar's generated Accounts::try_accounts includes header-level duplicate detection for mutable accounts. Passing the same account key in two mut positions is rejected at parse time. Framework: Quasar
```
```
Topic: Account Migration — Migration<From, To> Security
Applies to: Instructions performing schema migration between account versions

Migration<From, To> enforces at compile time: From::OWNER == To::OWNER (same program), From::DISCRIMINATOR is NOT a prefix of To::DISCRIMINATOR, target type fits in SPACE, target type < 3584 bytes (sBPF stack budget). At runtime: account must start with From::DISCRIMINATOR (not To::DISCRIMINATOR) before migration; after migration, account starts with To::DISCRIMINATOR. The migration type prevents using Signer accounts as source (compile fail). The migration target is written atomically. Developer must provide the new_data value for the target fields. QEDSpec: guard: account.data.starts_with(From::DISCRIMINATOR); ensures: account.data.starts_with(To::DISCRIMINATOR).
```

```
Framework: Quasar
Topic: #[instruction(raw)] — Fully Manual Handler
Applies to: Raw instruction handlers bypassing all account parsing

#[instruction(discriminator = N, raw)] emits the handler function unchanged. No account parsing, no constraint evaluation, no discriminator check, no signer verification. The handler receives Context with raw &[AccountView] and &[u8]. This is equivalent to native Rust with no framework. Every security property must be manually implemented: account.owner() == &expected, discriminator check, is_signer() check, PDA derivation. Combine with #[instruction(raw, heap)] to enable heap allocation. Use sparingly — prefer typed handlers. Any raw handler that reads account data without ownership and discriminator checks is a complete missing_ownership_check vulnerability.
```
